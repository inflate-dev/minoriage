## 1. 目的・背景

SfM（Structure from Motion）と YOLO による物体検出を連携させ、農園・畑などの対象空間の中に「何が」「どこに」「いくつ」あるかを 3D 空間上に表示できるようにする。ユーザーはスマートフォンでその空間の様子を直感的に把握できる。

## 2. 主な利用者

- 農家（一次ターゲット）

## 3. 現状のアプリ（As-Is）

現状は「単発の写真」を対象にした YOLO 検出＋在庫一覧アプリになっている。

- **カメラページ（`app/camera/page.tsx`）**
  - スマホカメラで静止画を1枚撮影
  - 画像をローカルサーバー（`SERVER_URL`）にアップロードし、YOLOの検出結果（ラベル・bbox）を取得
  - 撮影画像の上に検出ボックスを2D表示
  - 「記録」ボタンで Supabase に保存（`uploads` → `detections` → `inventory` → `inventory_detections` の4テーブル構成）
  - 当日の検出履歴を一覧表示
- **ダッシュボードページ（`app/dashboard/page.tsx`）**
  - 日/週/月/年ごとの検出数を集計してテーブル・棒グラフで表示（`/api/inventory-summary`）
  - 品目ごとの在庫数一覧（テーブル）
  - CSVエクスポート
- **データモデル（Supabase、既存テーブルから推測）**
  - `uploads`：アップロード単位（画像1枚 = 1件）
  - `detections`：検出結果（`object_type`, `bbox`, `upload_id`）
  - `inventory`：確定した在庫記録（`upload_id`, `user_id`, `company_id`, `confirmed_at`）
  - `inventory_detections`：`inventory` と `detections` の紐付け（`quantity`）

この「写真1枚→2D検出→一覧」の仕組みを、「動画→SfM再構成→3D空間上の検出結果一覧」に改造する。

## 4. 新機能要件（To-Be）

### 4.1 動画撮影・アップロード
- iPhone（スマホブラウザ）で対象空間（畑・農園）を撮影する
- アプリ内に「録画」ボタンを設け、撮影開始→撮影終了後に自動でバックエンド（自宅Jetson）へアップロードする
- 現行のカメラページ（静止画1枚撮影・2D検出表示）は廃止し、この動画撮影フローに一本化する
- 撮影時間の上限・ファイルサイズ・通信量の許容範囲は未定（今後、実機検証しながら決める）

### 4.2 SfM連携
- アップロードされた動画からSfM処理を行い、対象空間の3D構造（カメラ位置・点群など）を復元する
- SfM処理は自宅Jetsonで実行する

### 4.3 YOLO検出との連携
- 動画に対してYOLOによる物体検出を行う（検出対象は顧客ごとに異なる。まずは柿農家向けに柿を検出）
- 検出結果をSfMで復元した3D空間上の位置に紐付ける（どの検出が3D空間のどこに対応するか）
- 検出とSfM結果の紐付けロジックはバックエンド（Jetson）側の関心事であり、本アプリ（フロントエンド）の仕様としては扱わない

### 4.4 3D空間表示

- スマホのWebブラウザ（本Webアプリ）上で、SfMで復元した対象空間を3D表示する（three.js等のWebGLライブラリを利用）
- ユーザーが指操作で空間を回転（くるくる回す）・ズームできるインタラクティブなビューアとする
- その空間上に、検出した対象物の位置を重ねて表示する

**UIイメージ（参考モックアップより）**：ユーザーが用意した参考画像をもとに、以下の要素を含める。

- 画面左上の統計パネル：点群数／カメラ視点数／検出した対象物の総数（うち「複数視点で確認」「単一視点のみ」の内訳）
- 対象物マーカーの色分け：**複数のカメラ視点から確認できた対象物＝緑（信頼度高）**、**単一視点からしか確認できなかった対象物＝黄（信頼度低）**。この判定には「その対象物が何台のカメラ視点から見えていたか」（`view_count`）という値が必要で、YOLOの検出信頼度（`confidence`）とは別軸の情報として9章のAPIに追加する
- カメラ軌跡の表示：Jetsonが動画から復元したカメラの動きを線（赤）で表示。9章のAPIに`camera_trajectory`として追加する
- 画面右上の表示設定パネル：「カメラ軌跡を表示」「単一視点の対象物を表示」のON/OFFトグル、点の大きさスライダー
- インタラクション：対象物マーカーにカーソルを合わせると詳細（ラベル・視点数）をツールチップ表示、クリックでその対象物にカメラをフォーカスする
- 画面左下に凡例（密点群／カメラ軌跡／複数視点で確認／単一視点のみ、の色の意味）

### 4.5 在庫一覧表示
- 3D空間に存在する対象物を、「何が」「何個」あるかの一覧表（テーブル）でも表示する
- この一覧表は新規の「3D空間ビュー」ページ内に、3Dビューと合わせて表示する（既存ダッシュボードとは別画面。既存ダッシュボードの日次集計・在庫一覧は変更しない）

## 6. データフロー概要（案）

```
[スマホで動画撮影]
   ↓
[バックエンドへ動画アップロード]
   ↓
[SfM処理] → 3D空間構造（点群・カメラ位置）
[YOLO検出] → フレームごとの物体検出結果
   ↓
[検出結果を3D空間上の位置に紐付け]
   ↓
[スマホ側（新規「3D空間ビュー」ページ）で3D空間表示 + 対象物一覧表示]
```

※ SfM処理・YOLO処理はいずれも自宅Jetson上で行う。検出結果とSfM結果（3D空間上の位置）の紐付けロジックもJetson側（バックエンド）の実装であり、本アプリの仕様としては「紐付け済みの結果を受け取って表示する」ところが対象範囲となる。

## 7. 要確認事項（この仕様書を確定させるために必要な情報）

1. **SfM処理の実行場所**：✅ 自宅に設置した Jetson で計算する（既存の「ローカルサーバー」＝YOLO検出を行っているマシンと同一と想定。SfMもここで処理する方針）

2. **3D表示の実現方法**：✅ このNext.js Webアプリ上（スマホブラウザ）で実現する。空間を回転（くるくる回す）・ズームできるインタラクティブな3Dビューアが必要（three.js等のWebGLライブラリを利用する方針）
3. **動画の仕様**：✅ iPhoneを想定。アプリ内に「録画」ボタンを設け、撮影→撮影終了後に自動でアップロードする流れとする。撮影時間の上限・ファイルサイズ・通信量の許容範囲は現時点で未定（今後、実機検証しながら決める）
4. **検出とSfMの紐付け方法**：✅ バックエンド（Jetson）側の処理の関心事であり、本アプリ（フロントエンド）の仕様としては扱わない。本仕様書のスコープ外とする
5. **既存フローとの関係**：✅ 現行の「写真1枚→2D検出→記録」フロー（カメラページの静止画撮影・2Dバウンディングボックス表示）は廃止し、動画撮影フローに一本化する
6. **検出対象**：✅ 検出対象は顧客（利用農家）ごとに異なる想定。まずは柿農家を想定し、柿を検出対象とする（将来的に他の作物にも対応できる前提でクラス設計・UI表現を考える）
7. **利用環境**：✅ まずはオフライン保存・アップロードリトライは対応しない（電波がある環境での利用を前提とする）。必要になった場合は将来の追加機能として扱う

## 9. Jetson API・処理待ちの方式（追加検討事項）

1. **処理完了の確認方式**：✅ ポーリング方式を採用する
   - 動画アップロード時、Jetsonは即座に「受付ID」（`scan_id`）を返す
   - アプリ側はその受付IDを使い、`GET /scan/status/{scan_id}` を10〜15秒間隔で呼び出して進捗を確認する
   - Jetsonが「処理中」を返している間はポーリングを継続し、「完了」になったら結果取得APIを1回呼んで3D空間ビューに表示する
   - Webhook／プッシュ通知方式は不採用（スマホブラウザは常時接続の待ち受けができず、実装コストが高いため。Jetson1台構成のシンプルな個人開発にはポーリングで十分）

2. **3D結果のデータ形式**：✅ 点群（point cloud）＋ **PLY形式**で転送する（v0.8で glTF/.glb から変更）
   - **点群 vs メッシュ**：点群（SfMの生の出力＝空間内に打たれた点の集まり）を採用。メッシュ（点を三角形でつないだ面）は計算負荷・処理時間が増えるため今回は不採用。「畑の様子を把握できればよい」という目的には点群で十分
   - **転送形式**：当初glTF（`.glb`）を想定していたが、実際にSfM/YOLO側を検証したところCOLMAPの密点群出力（`stereo_fusion`）はbinary PLY（`x,y,z,nx,ny,nz,r,g,b`）が自然な出力形式で、glTFへの変換ステップはJetson側に未実装だった。three.jsには`PLYLoader`が標準で用意されており、glTFと同様「フロントエンドで独自パース不要」という条件を満たせるため、**PLYをそのまま返す方式に変更**し、Jetson側の変換ステップを不要にした
   - Jetsonは処理完了後、点群を`.ply`（binary_little_endian）として書き出し、そのURLを結果APIで返す
   - **座標スケールの注意**：SfMの復元結果は基本的に任意スケールで、実世界の「メートル」に対応しない。Jetson側で実施している`pycolmap.align_reconstruction_to_locations()`によるSim3dアライメント（ground合わせ）済みの復元結果のみを本APIで返すこと。ground合わせ未実施の結果を返すと、点群とマーカー・カメラ軌跡のスケール感が噛み合わなくなる
   - フロント側の対策として、対象物マーカーの大きさは固定値ではなく点群のバウンディングボックスに対する相対サイズで描画し、スケールが多少ずれても破綻しないようにする（`components/ScanViewer.tsx`）

3. **エンドポイント案**

   | メソッド | パス | 役割 |
   |---|---|---|
   | POST | `/scan/upload` | 動画アップロード（`multipart/form-data`：video, user, company）。即座に`scan_id`を返す |
   | GET | `/scan/status/{scan_id}` | 進捗確認用（ポーリング）。軽量なレスポンスのみ返す |
   | GET | `/scan/result/{scan_id}` | 完了後の結果取得。点群（`.ply`）のURL＋検出結果JSONを返す |

   ```json
   // GET /scan/status/{scan_id}
   { "status": "processing", "stage": "sfm_running" }
   // または { "status": "done" } / { "status": "failed", "error": "..." }

   // GET /scan/result/{scan_id}
   {
     "scan_id": "abc123",
     "pointcloud_url": "https://jetson.example.com/scan/abc123/pointcloud.ply",
     "camera_trajectory": [
       { "x": 0.0, "y": 0.0, "z": 0.0 },
       { "x": 0.1, "y": 0.02, "z": 0.05 }
     ],
     "objects": [
       {
         "id": "obj-1",
         "label": "kaki",
         "position": { "x": 1.2, "y": 0.4, "z": 3.1 },
         "confidence": 0.91,
         "view_count": 3
       }
     ],
     "summary": { "kaki": 128 }
   }
   ```
   - status/resultを分けているのは、頻繁に叩くポーリング（status）で毎回重い点群データを返さないようにするため
   - `camera_trajectory`：SfMで復元したカメラの位置を撮影順に並べた配列（点群と同じ座標系）。3Dビュー上にカメラの軌跡として線で表示する（4.4節のUIイメージ参照）。点数は少ない（カメラ視点の数＝数十点程度）ため、点群のように別ファイル化せずJSONに含めてよい。Jetson側は`pycolmap`の`Reconstruction.images`から`has_pose`な画像を撮影順にソートし`projection_center()`を並べることで生成できることを確認済み（外れ値除去つき）
   - `objects`の`label`/`confidence`/`view_count`は、SfM/YOLO検証側の実装で自然に出てくるフィールド名（`class_name`/`mean_conf`/`num_views`）とは異なる。**この名前はフロントエンドとJetsonの合意済みインターフェースなので、Jetson側の`/scan/result`実装でリネームして返す**（アダプター層を1枚挟む想定）。`source_images`（元画像ファイル名リスト）など、ここに無い追加フィールドが混ざっていてもフロント側は無視するだけなので問題ない
   - `view_count`：その対象物が何台のカメラ視点から確認できたか。SfMは複数の写真（フレーム）から同じ対象物を三角測量するため、2視点以上から確認できたものは位置の信頼性が高く、1視点のみのものは信頼性が低い。この値を使って3Dビュー上でマーカーの色を分ける（緑＝2視点以上、黄＝1視点のみ）。`confidence`（YOLOの検出信頼度）とは別軸の情報

4. **Jetsonへの通信の認証方式**：✅ APIキーによる認証を追加する

   **現状の課題**：現行の`app/camera/page.tsx`（`sendToLocalServer`）はJetsonへのアップロードに認証が一切ない。`company`/`user`もフォーム値としてクライアントが自由に指定でき、なりすましが可能。未ログイン時はハードコードされたUUIDにフォールバックする実装になっている。今まではLAN内限定だったため実害が小さかったが、Jetsonをインターネットに公開する今回の方針では対策が必須。

   **対応方針**：
   - Jetson側のAPIに固定のAPIキーを設定し、リクエストヘッダー `Authorization: Bearer <API_KEY>` を必須にする。キーが一致しない場合は401を返す
   - アプリ側は`.env.local`にそのAPIキーを保持し、`/scan/upload` `/scan/status` `/scan/result` すべてのリクエストにヘッダーとして付与する
   - `company`/`user`はクライアントのフォーム値をそのまま信用せず、Supabaseのログインセッション（`user`ストア）から取得した値のみを使う。未ログイン時にハードコードされたUUIDへフォールバックする現行の実装は廃止し、未ログインなら撮影・アップロード自体をさせない（ボタン無効化 or ログイン画面へ誘導）
   - 通信はHTTPS化する（自己署名証明書 or 無料証明書での対応を検討）

5. **履歴機能・失敗時のエラー表示**：✅ どちらも実装する
   - 過去のスキャン結果を後から一覧で見返せるようにする
   - SfM/検出が失敗した場合、その旨と理由をアプリ上に表示する
   - どちらも下記6章のテーブル設計（`scans`テーブルの`status`/`error_message`）で実現する

## 10. Supabaseテーブル設計（案）

現行の`uploads`/`detections`/`inventory`/`inventory_detections`は「写真1枚＋2D bbox」を前提にした構造なので、動画スキャン＋3D座標を扱う新しいテーブルを追加する（既存テーブル・既存ダッシュボードには手を加えない）。

### `scans`（1回の動画スキャン＝1レコード）

| カラム | 型 | 説明 |
|---|---|---|
| `id` | uuid (PK) | スキャンID（アプリ内部の主キー） |
| `user_id` | uuid | 撮影したユーザー（Supabase Authのuser.id） |
| `company_id` | uuid | 所属会社（`profiles.company_id`） |
| `jetson_scan_id` | text | Jetsonが発行した`scan_id`（ポーリングに使う） |
| `status` | text | `uploading` / `processing` / `done` / `failed` |
| `error_message` | text (nullable) | 失敗時の理由（Jetsonの`/scan/status`の`error`をそのまま保存） |
| `pointcloud_url` | text (nullable) | 完了後の点群（`.glb`）URL |
| `camera_trajectory` | jsonb (nullable) | カメラ軌跡の座標列（`[{x,y,z}, ...]`）。点数が少ないので単一カラムにJSONで保存 |
| `video_url` | text (nullable) | 元動画の保存先URL（保存する場合のみ。保存方針は要検討＝8章参照） |
| `created_at` | timestamptz | 撮影・アップロード開始日時 |
| `completed_at` | timestamptz (nullable) | 処理完了（成功/失敗確定）日時 |

### `scan_objects`（スキャン内で検出された対象物、1件＝1個体）

| カラム | 型 | 説明 |
|---|---|---|
| `id` | uuid (PK) | |
| `scan_id` | uuid (FK → `scans.id`) | どのスキャンに属するか |
| `label` | text | 対象物の種類（例：`kaki`） |
| `position_x` / `position_y` / `position_z` | float8 | 点群と同じ座標系での3D位置 |
| `confidence` | float4 | YOLOの検出信頼度 |
| `view_count` | int | 何台のカメラ視点から確認できたか（3Dビューでのマーカー色分けに使用。9章参照） |

**設計のポイント**：
- 「品目ごとの個数」は集計せず保存しない。`scan_objects`を`label`でグルーピングして`COUNT(*)`すれば在庫一覧（4.5節）の表示に使える（例：`SELECT label, COUNT(*) FROM scan_objects WHERE scan_id = ? GROUP BY label`）。数を別カラムで二重管理すると不整合の元になるため
- **履歴一覧**：`scans`を`user_id`（または`company_id`）で絞り、`created_at`降順で並べれば実現できる
- **失敗表示**：`status = 'failed'`のスキャンは`error_message`をそのまま画面に出す
- 既存テーブルと同様、Row Level Security（RLS）で`user_id`/`company_id`によるアクセス制限をかける想定（既存ポリシーを踏襲）

## 11. 実装時に決める細部（仕様書レベルでは確定不要）
- エンドポイントのHTTPステータスコード・フィールド名などの細部（実装しながら自然に決める）

## 12. 元動画の保存方針

✅ 元動画は基本的に保存する。削除機能は不要（今回は実装しない）。

- `scans.video_url`に撮影した動画のURLを保存し、そのまま残す
- ストレージ容量が将来的に問題になった場合は、その時点で削除・アーカイブ機能を追加検討する（現時点ではスコープ外）
